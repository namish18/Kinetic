# Contributing to Kinetic

First of all, thank you for your interest in contributing to **Kinetic!** We appreciate developers, designers, researchers, and open-source enthusiasts who want to help improve the project.

Kinetic aims to build a meritocratic funding platform for open-source contributors. Every meaningful contribution matters, whether it is fixing a bug, improving the UI, enhancing documentation, or strengthening an existing feature.

We welcome contributions from everyone, but we ask all contributors to follow the guidelines below to maintain code quality, consistency, and architectural integrity.

---

## 1. Before You Start

**Please check existing issues before starting any work.**

Our preferred contribution workflow is to work on issues that have already been created and discussed.

- Visit the [GitHub Issues](https://github.com/namish18/Kinetic/issues) page.
- Look for open issues that need attention.
- Check whether someone is already working on the issue.
- Comment on the issue expressing your interest before starting implementation.
- Wait for confirmation or clarification from the maintainers if necessary.

### When should you create a new issue?

We strongly prefer contributors to work on existing issues rather than continuously creating new ones.

Create a new issue only when:

- You have identified a **critical bug** that has not already been reported.
- You are proposing a **major feature** that could meaningfully improve Kinetic.
- You have identified a significant security, performance, or reliability concern.
- The problem or proposed improvement is not covered by any existing issue.

For minor improvements, small UI adjustments, code cleanup, and similar changes, please check existing issues or discuss your proposal before opening something new.

**Avoid creating duplicate issues.** Always search the issue tracker before submitting a new one.

---

## 2. Respect the Existing Architecture

This is one of the most important guidelines for contributing to Kinetic.

Kinetic has an established architecture consisting of:

- **Frontend:** Next.js, React, Tailwind CSS.
- **Backend:** Node.js, Express.js, MongoDB, and Passport.
- **Blockchain:** Flow Testnet, Cadence, and Flow Client Library (FCL).
- **Decentralized Infrastructure:** DID, Helia, and IPFS integrations.

The existing architecture and technology choices are intentional.

### What we expect:

- Work within the existing project structure.
- Reuse existing components, services, utilities, and APIs wherever possible.
- Follow established coding patterns and conventions.
- Keep changes modular and limited to the scope of your issue.
- Maintain compatibility with existing functionality and integrations.

### What you should NOT do:

- Do not redesign or replace the core architecture.
- Do not introduce a new framework, database, or major dependency without prior approval.
- Do not restructure major directories or reorganize the entire codebase unnecessarily.
- Do not modify core business logic, scoring mechanisms, authentication flows, DID infrastructure, or blockchain integrations without discussing the changes with maintainers first.
- Do not introduce breaking changes to existing APIs or workflows without prior approval.

**If you believe a change requires architectural modifications, open a discussion with the maintainers before implementing it.**

We encourage improvements, not unnecessary architectural rewrites.

## 3. AI-Assisted Coding Policy

AI-assisted development is absolutely allowed!

You are free to use tools such as:

- GitHub Copilot
- ChatGPT
- Claude
- Cursor
- Windsurf
- Gemini
- Other AI-powered development tools

We do not restrict how you write your code. However, **you are responsible for every line of code you submit, regardless of whether it was written manually or generated using AI.**

### Important expectations:

- Understand the code generated by AI before submitting it.
- Review the generated implementation for correctness and security.
- Ensure it follows the existing architecture and coding conventions.
- Check for unnecessary dependencies, duplicated logic, and unintended changes.
- Verify that the implementation does not break existing functionality.

### Test before submitting!

**Do not blindly generate code using AI and immediately raise a Pull Request.**

Once your implementation is complete:

1. Run the application locally.
2. Test the complete workflow affected by your changes.
3. Verify that the new functionality behaves as expected.
4. Check that existing functionality still works.
5. Review the browser console and backend logs for errors.
6. Fix any issues you encounter before submitting your PR.

AI-generated code is welcome. Unverified AI-generated code is not.

## 4. Getting Started

### Prerequisites

Make sure you have the following installed:

- Node.js v20 or later
- npm v9 or later
- Git
- MongoDB (local instance or MongoDB Atlas)
- Flow CLI (only if working on smart contracts or Flow-related functionality)

Refer to the main [README](https://github.com/namish18/Kinetic#readme) for environment configuration and setup instructions.

### Fork the Repository

1. Fork the [Kinetic repository](https://github.com/namish18/Kinetic).
2. Clone your fork:

   ```bash
   git clone https://github.com/<your-username>/Kinetic.git
   ```

3. Navigate to the project directory:

   ```bash
   cd Kinetic
   ```

4. Add the original repository as the upstream remote:

   ```bash
   git remote add upstream https://github.com/namish18/Kinetic.git
   ```

### Set Up the Backend

```bash
cd backend
npm install
```

Configure your `.env` file according to the environment variables documented in the README.

Start the backend:

```bash
npm run dev
```

### Set Up the Frontend

Open another terminal:

```bash
cd frontend
npm install
npm run dev
```

The frontend should be accessible at:

```text
http://localhost:3000
```

The backend API should be accessible at:

```text
http://localhost:5000
```

## 5. Development Workflow

Once you have selected an issue and are ready to work:

### Step 1: Sync Your Fork

```bash
git checkout main
git fetch upstream
git merge upstream/main
```

### Step 2: Create a Separate Branch

Use descriptive branch names.

Examples:

```bash
git checkout -b fix/contribution-dashboard
git checkout -b feat/improve-user-profile
git checkout -b docs/update-api-documentation
```

Recommended prefixes:

- `feat/` – New functionality
- `fix/` – Bug fixes
- `docs/` – Documentation changes
- `refactor/` – Code improvements without changing functionality
- `test/` – Test-related changes

### Step 3: Implement Your Changes

- Keep your changes focused on the assigned issue.
- Avoid modifying unrelated files.
- Follow the existing coding style.
- Add or update tests where applicable.
- Update documentation when necessary.

### Step 4: Test Your Implementation

Before committing, make sure you have tested the actual workflow.

A successful compilation alone does not guarantee that a feature works correctly.

### Step 5: Commit Your Changes

Write meaningful commit messages.

Examples:

```bash
git commit -m "fix: resolve contribution dashboard loading issue"
git commit -m "feat: improve contributor profile experience"
git commit -m "docs: update API documentation"
```

### Step 6: Push Your Branch

```bash
git push origin your-branch-name
```

### Step 7: Open a Pull Request

Create a Pull Request against the `main` branch of the original repository.

## 6. Pull Request Guidelines

We want Pull Requests to be easy to review, understand, and maintain.

Every PR should:

- Have a clear and descriptive title.
- Explain what was changed and why.
- Reference the relevant existing issue using `Closes #ISSUE_NUMBER` where appropriate.
- Include screenshots or recordings for UI-related changes.
- Mention the testing performed.
- Highlight any dependencies or configuration changes.
- Contain only relevant changes.

### Before submitting a PR, verify:

- [ ] My changes address the intended issue.
- [ ] I have followed the existing architecture.
- [ ] I have tested the affected workflow locally.
- [ ] Existing functionality has not been unintentionally broken.
- [ ] I have removed debugging statements and unnecessary code.
- [ ] I have not committed secrets, credentials, or `.env` files.
- [ ] I have reviewed my own changes.
- [ ] I have included relevant screenshots or testing details.

**Important:** Pull Requests that introduce untested code, unrelated changes, unnecessary architectural modifications, or duplicate implementations may be sent back for revisions or rejected.

Maintainers may request changes before merging. Please be open to feedback and collaborate constructively.

## 7. Areas Where You Can Contribute

Here are some areas where contributions can make a difference:

- **Frontend:** Dashboard improvements, UI/UX enhancements, responsiveness, accessibility, and reusable components.
- **Backend:** API improvements, error handling, performance, and reliability.
- **Contribution Scoring:** Improvements to the MSTS scoring engine, subject to maintainer discussion and approval.
- **Blockchain:** Flow integration, Cadence contracts, and transaction handling, subject to prior discussion.
- **Decentralized Identity:** Improvements to DID resolution, verification, and IPFS integration.
- **Testing:** Unit tests, integration tests, and workflow validation.
- **Documentation:** Setup instructions, API documentation, technical explanations, and developer guides.
- **Security:** Identifying vulnerabilities and suggesting improvements through responsible disclosure.

For changes involving core scoring, identity, authentication, or payout logic, always discuss the proposed approach with maintainers first.

---

## 8. Security and Sensitive Information

Please follow these security practices:

- Never commit API keys, private keys, passwords, OAuth secrets, or other credentials.
- Never expose private environment variables in frontend code.
- Do not commit `.env` files.
- Do not include real user credentials or private information in test data.
- Report security vulnerabilities responsibly rather than publicly disclosing exploitable details.

---

## 9. Community Expectations

We want Kinetic to be a collaborative and welcoming open-source project.

We expect every contributor to:

- Be respectful and professional.
- Communicate clearly.
- Accept constructive feedback.
- Avoid unnecessary arguments and duplicate discussions.
- Give credit where it is due.
- Help other contributors when possible.

Quality and meaningful contributions matter more than the number of commits or Pull Requests.

---

## 10. Final Note

Kinetic is a community-driven project, and we genuinely appreciate everyone who invests their time and effort into improving it.

A few things we would like every contributor to remember:

1. **Prioritize existing issues.** Do not create new issues for every small improvement.
2. **Respect the architecture.** Improve what exists instead of unnecessarily rebuilding it.
3. **AI is welcome.** But understand, review, and test everything it generates.
4. **Test your work.** Never submit a PR without verifying the actual workflow.
5. **Keep contributions focused.** Small, well-tested, meaningful PRs are better than massive, unverified changes.

We are excited to have you contribute to Kinetic!

**Happy Coding! 🚀**

— Kinetic Maintainers
